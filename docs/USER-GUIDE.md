# Crawlvora — Court Registry workspace

The sole online collection source is the Croatian Court Registry public v3 API. Existing local company records, source provenance and job history are retained. Web scraper jobs from old versions are cancelled rather than executed. CSV/JSON import and directory/registry exports remain available.

## Desktop window

Crawlvora starts as a centered, resizable window, targeting 1120 × 720 logical pixels and limiting initial size to the available monitor work area with a margin. Compact layouts reflow as the window narrows; wide tables can scroll within their own container. Native maximize remains an explicit user action, not a startup default.

## Connection

In Settings → API access, enter your authorized Client ID and Client Secret. Select the secure storage consent checkbox and apply the credentials to retain the pair across restarts using the OS-protected vault (Windows DPAPI or Linux Secret Service). Without consent, the pair is session-only. A previously saved pair remains available after restart unless you explicitly remove saved access. The vault is isolated from the backup catalog and scoped to the current workspace. Linux requires an available, unlocked Secret Service. Secure storage failure is reported and never creates a plaintext file. The Court Registry permission checkbox is selected when saved consent is active; click Synchronize to authenticate and request real records. A configured status is not proof of successful OAuth or live access.

Remove saved access to clear the stored registry pair and session override. This does not revoke credentials at the official provider or remove separately provisioned environment variables or private files; revoke those through their respective authorized management channels. Stop synchronization before removing access; the worker rejects removal while synchronization is active. Disable scheduled refresh and revoke provider credentials separately if required. A temporarily unavailable OS vault is retried after a bounded cooldown.

Administrators may still privately provision both SUDREG environment variables or a private workspace configuration file. If either variable is set, the environment pair is used as a unit, never mixed with another source. Explicit session credentials override other sources for the session. On restart, environment credentials take precedence over the OS vault, then legacy private configuration. The arbitrary working directory is not searched. Never commit credentials or embed shared secrets in public packages. Managed installations can enroll automatically on first native launch: the authorized deployment system supplies both SUDREG_CLIENT_ID and SUDREG_CLIENT_SECRET and sets CRAWLVORA_REGISTRY_PROVISION=1 in the launching user's private process environment. The packaged worker consumes the pair, stores it in the current user's OS vault and uses saved authorization on later launches. No manual upload or repeat confirmation is required. Launch under the intended desktop user with an unlocked vault, remove provisioning variables from the deployment environment after enrollment, and do not set them in a public installer or global environment. Invalid or incomplete enrollment fails closed without creating a plaintext file; the offline app remains available. Public installations without an authorized pair cannot contact the official API until an authorized deployment or one-time enrollment. No remote automatic account creation is supported. Scheduled refresh requires valid credentials and a running app.

## Existing data

The bundled original CSV contains 26,261 records and is seeded only once. Existing databases are not replaced. Reimport merges compatible OIB/MBS identifiers and conservative name/city/address matches; conflicting identifiers are not silently merged. Old sources remain visible solely as provenance, not as selectable online collection services. Import additional CSV/JSON through Import & Export.

## Synchronization

Use Court Registry to synchronize public bulk categories with the same snapshot ID, resume interrupted pages, browse records, compare completed snapshots and export. Official data updates compatible identity fields while retaining existing contacts. Tasks & Schedule provides the registry-only queue and weekday refresh.

Live credentials, complete synchronization, platform packaging and exact design parity must be verified before a production release.

## Data protection

Every normal launch acquires an OS workspace lock and creates a verified SQLite online backup before modifying an existing database. Backups are stored in the workspace's `backups` directory and are never automatically deleted. A failed backup prevents opening the workspace for changes. First-time seed import and its completion marker commit atomically. Differing incoming nonempty field values are retained in the local alternate_values table. These safeguards do not guarantee survival of disk failure: keep independent encrypted backups. For recovery, close all instances, copy the entire current workspace to a separate location, then restore a verified backup into a new workspace; never overwrite the only original. Backups contain business/contact data and must remain private.

Manual CSV/JSON imports also create a verified backup before writing. Company Profile → Source Links displays preserved alternative values and their source; directory JSON export includes these values as well. Directory exports are not complete workspace backups (they do not restore registry snapshots, all provenance or application state). Use the verified SQLite backup for complete workspace recovery. JSON import remains a directory import, not a database restore.

## Verified offline recovery

From the source distribution, run `python tools/recover_workspace.py /path/to/backup.sqlite3 /path/to/new-workspace` (new directory must not exist; use a local filesystem supporting hard links, e.g. NTFS or ext4). The utility checks full SQLite integrity, foreign keys and required tables, then creates and verifies a separate database. It never replaces the original database or backup. To inspect the recovered workspace using the source application, run `python src/tvrtk_scraper.py --data-dir /path/to/new-workspace`. Private credentials are not restored. The packaged desktop recovery UI and workspace selector are not implemented yet. Process-exit testing is not physical power-loss testing. Keep independent backups.

Settings → Backup & Recovery creates a consistent local backup, downloads it to a user-selected location through the webview, restores a selected local copy into a new workspace, and shows a read-only count and up to ten company names. No active database is replaced. Save the downloaded unencrypted copy to a separate physical disk with appropriate access controls. Activating a recovered workspace as the desktop application's main database is not yet implemented. Search `oib:12345678901` or `mbs:123456789` for exact indexed identifiers; ordinary free-text search remains unchanged. Backup and recovery controls extend the existing Settings design; an updated visual reference and native download verification are still required.

Settings → Backup & Recovery now persists the selected workspace for the next launch in a separate SQLite catalog. Both the original and recovered workspaces remain separate; no live database swap occurs. Close and reopen the application to activate. Use `--primary-workspace` on the native executable or source launcher to open the original without changing the saved selection if recovery fails. Recovered workspaces do not seed extra companies. Search `fts:some phrase` for indexed token/phrase search (case and diacritics insensitive); ordinary text search preserves prior substring semantics. FTS is a derived index maintained in the same transactions as the directory. If FTS5 is unavailable on a new database, explicit phrase search falls back to substring search. Native packages must pass FTS tests. A million-record benchmark is configured; results are not yet established.

Encrypted independent backups use AES-256-GCM with a random 96-bit nonce, random 128-bit salt and scrypt (N=131072,r=8,p=1) via PyCA cryptography. Enter and confirm a unique passphrase (at least 16 characters), then save the .cvbackup download on separate physical storage. The passphrase is not persisted. The source CLI `python tools/encrypted_recovery.py archive.cvbackup new-workspace` authenticates before publishing plaintext and validates the restored SQLite database. Existing files are never overwritten. The CLI requires a local filesystem supporting hard links; temporary plaintext exists in a private temporary directory during authenticated recovery and normal cleanup is not secure erasure. The graphical encrypted download currently buffers the encrypted archive in webview memory, so large-file native download and graphical encrypted restore remain release verification items. Local automatic SQLite backups remain unencrypted. Lost passphrases cannot be recovered.

A restored workspace preserves its historical scheduler and queue state. Saved registry tasks may resume if credentials are available; review the restored settings before enabling further automation. The restart regression test exercises primary → recovered → primary with the real authenticated worker, and browser integration checks the encrypted download header and clears passphrase inputs. These tests are pending CI confirmation.

Encrypted recovery is now available in Settings. Uploads stream a selected file to private temporary storage in 1 MiB blocks, limited to 32 GiB and available disk space; authentication precedes restoration. Export preparation returns a five-minute, one-use session-protected download ticket, then downloads the encrypted file directly without a JavaScript Blob. An expired unclaimed download is removed on the next preparation or normal process cleanup; abnormal termination can leave encrypted temporary files. Temporary plaintext during recovery is not securely erased. All discovered workspaces receive a read-only quick integrity check after startup; the full check is available in Settings. The active FTS5 logical index is checked and rebuilt only for recognized virtual-table corruption after startup backup. Physical database corruption is not automatically repaired. The active workspace fails closed on failed quick checks. Native verification is pending.

The streaming regression tests cover bounded reads, short uploads, one-use download tickets, wrong passphrases, restoring into a separate workspace and rebuilding a deliberately inconsistent derived FTS index without modifying company records. The benchmark now asserts FTS availability and checks identical results for a selective phrase before measuring. Numeric reports are printed to CI logs as well as saved as artifacts.

## Protected automatic backups

Open Settings → Backup & Recovery → Protected automatic backups. Initialize the catalog using a unique passphrase of at least 16 characters, or unlock the existing catalog. The passphrase and derived catalog authentication key are held only for the unlocked application session; no plaintext key file or hardcoded key is used. Automatic encrypted copies are scheduled every six hours and a catalog verification every 24 hours while unlocked. A verified encrypted copy is created before manual imports while unlocked; when locked, the existing unencrypted safety backup remains in use. The original startup backup remains unencrypted. No legacy copies are removed. The per-workspace catalog uses a passphrase-derived HMAC-SHA256 chain, authenticated head, SHA-256 ciphertext digests and SQLite FULL synchronous transactions. An archive committed before a crash but not registered in the catalog is reported as an orphan and retained; it can be recovered by the existing encrypted-file restore with the original passphrase. Catalog-authenticated restore creates a separate workspace, never silently activates it. A complete rollback of the catalog and archive directory cannot be detected without an independent trusted anchor. Periodic checks verify ciphertext against authenticated digests, not a full decrypt/restore of every archive. Secure erasure of temporary plaintext, unattended restart unlocking, OS-backed key storage and independent off-device replication are not implemented. Keep the passphrase and independently downloaded encrypted archive on separate storage. If the application cannot start, use the offline encrypted recovery utility from the source distribution.

The protected backup test suite now covers scheduled creation while unlocked, no repeated creation before the interval, locked-session behavior and forced child-process exit after encrypted archive publication but before catalog registration. The orphan remains recoverable using the existing encrypted-file recovery flow. The application never automatically switches to a stale backup.

## Native vault and independent replication

Opt in to secure key storage after unlocking an existing protected catalog. Windows uses user-scoped DPAPI with workspace-specific entropy and a separate profile directory; Linux uses `secret-tool` with the desktop Secret Service. No plaintext credential file is written. The Linux session must have an available, unlocked Secret Service. The vault holds the passphrase and an external catalog checkpoint, not a hardware monotonic counter. A prepared checkpoint is written before the catalog transaction and advanced after the exact new head is observed. An ambiguous old head after preparation fails closed and retains the archive for manual recovery. A missing enrolled vault is not silently replaced. This detects rollback of the workspace catalog against an intact vault; simultaneous rollback/deletion of both trust stores is not guaranteed detectable. Keep an independent passphrase and archive. Native vault loss does not delete existing data or prevent independent encrypted-file recovery. The existing unencrypted startup/locked-session safety copies remain.

Choose an existing directory on a separately mounted physical disk, then save the replica destination. The app rejects the source filesystem, copies authenticated archives without overwrite, checks SHA-256 and writes unique catalog snapshots. A different filesystem does not prove separate physical hardware. The target must support hard links (e.g. NTFS/ext4); external FAT/exFAT is not supported by the atomic publication path. Replica creation runs after new protected backups; errors retain the local copy. A restore test authenticates, decrypts and restores the selected archive into a temporary separate database, runs full integrity checks, and reports the company count. No automatic activation occurs. The vault, actual independent disk, native recovery downloads and power-loss behavior require final platform verification.

## Replacement-computer recovery

Export the authenticated recovery manifest alongside the selected protected archive and retain your original passphrase independently. The source utility `python tools/portable_recovery.py manifest.json protected-<id>.cvbackup new-workspace --expected-head <trusted-head>` verifies HMAC, archive digest, AES-GCM authentication and SQLite integrity before creating a separate workspace. The optional expected head must come from an independent trusted checkpoint, not the same potentially rolled-back disk. This is passphrase-based recovery, not an export of the machine-specific DPAPI/Secret Service secret. Replication writes per-archive manifests named with their catalog head. A new prepared vault checkpoint includes the signed entry so a verified interrupted append can roll forward exactly; older incomplete checkpoints lacking the entry remain blocked. No old catalog or archive is silently discarded.

The Recovery Center provides Download recovery manifest for the selected verified protected archive. Replication reuses a single authenticated catalog read instead of repeatedly reading the full catalog for each archive. Direct Linux block devices on the same physical disk are rejected even if partition filesystems differ. Virtual, network, RAID/LVM and Windows physical storage topology remain unverified; a separate filesystem is still not a universal physical-separation guarantee. A dedicated native vault acceptance workflow exercises real Windows DPAPI and an isolated Linux Secret Service session. Results must be checked before release.


### Official public reference model

The supplied v3 reference schema defines 33 tables, including SUBJEKTI, TVRTKE (IME), SKRACENE_TVRTKE (IME), SJEDISTA (NAZIV_NASELJA, NASELJE_VAN_SIFRARNIKA, KUCNI_PODBROJ, POSTANSKI_BROJ) and EMAIL_ADRESE (ADRESA). Directory projection supports these fields, preferring full names, then short names, then the documented deletion-time name. All raw public rows and additional email addresses remain in the snapshot. Existing contacts are retained by the directory merge policy. Records without an identifiable name or MBS remain in the raw snapshot and are counted as skipped for the directory. Reference-shaped synthetic tests cover projection; live API shape and full category coverage still require authorized verification. Credentials are never committed to source or public releases.


## Private preconfigured Windows packages

For the owner's private Windows deployment, run `windows/build-private.ps1` in the intended user's Windows session on the target computer, with the normal native build prerequisites installed. The build obtains the authorized pair privately (both SUDREG variables supplied for this process, or hidden interactive input at build time), encrypts it using user-scoped DPAPI and embeds the encrypted capsule in the native worker inside Portable.exe. Setup.exe installs that same embedded-worker host. Both packages are created in ignored `dist/private-release/`, with SHA256SUMS.txt, not the public release-assets directory. No additional file, credential input or environment configuration is needed at application runtime on that Windows profile. The capsule is bound to the originating user/profile; it is not a cross-machine credential transport. Existing vault records and explicit revocation tombstones are never overwritten by a capsule. Native smoke tests suppress enrollment. The private builder is not executed by public release workflows; do not publish its outputs or use a cloud runner for this DPAPI-bound build. This path requires native build and authorized live API verification. Linux retains its separate secure managed provisioning mechanism.

The private builder now requires a successful live OAuth2 token exchange, OpenAPI discovery and one snapshot-consistent public company row before creating its DPAPI capsule. Only counts and generic errors are printed. The private portable host and a separate installer acceptance variant (isolated AppId, same embedded binary) must pass launch/install/uninstall checks before the two final packages are copied to the private output directory. This is a bounded smoke test, not proof that all registry records have been downloaded.


### Complete public registry scope

The official v3 developer instructions state that omitted only_active defaults to active rows. Crawlvora now explicitly sends only_active=false whenever the public OpenAPI endpoint supports the parameter. Snapshot manifests distinguish all-status scope from older active-only snapshots; existing older snapshots are preserved and cannot be silently promoted to a complete all-status mirror. If an older scope uses the same snapshot ID, use a fresh dedicated workspace or a new snapshot. A successful one-row API smoke test is not proof of complete synchronization. The official dataset is provided under the Croatian Open Licence: https://mpudt.gov.hr/otvoreni-podaci/24346 . Any redistribution must identify the source and snapshot date and exclude private credentials and separately imported user data.


## Complete distribution snapshot acceptance

Run `python tools/build_registry_bundle.py registry-bundle` in a dedicated directory with authorized credentials in the process environment or via its local hidden input. The collector writes only official registry rows, with resumable checkpoints. It does not open or publish the user's existing workspace. The verifier requires a single completed all-status snapshot, at least the previously observed 36 public categories, contiguous page offsets, matching payload hashes and row counts, unique normalized subject MBS, complete subject coverage in the directory and SQLite integrity/foreign-key checks. Failure retains local checkpoints but does not create an accepted manifest. The GitHub manual workflow uses the production-api environment secrets SUDREG_CLIENT_ID and SUDREG_CLIENT_SECRET; no secrets in source or packages. Its verified snapshot artifact is a prerequisite for, not proof of, a subsequent data-bearing release. Hosted jobs have a six-hour limit; full synchronization can require a longer local run. Source: Croatian Court Registry public v3, Croatian Open Licence (https://www.data.gov.hr/hr/open-license). Do not redistribute private imported data or credentials. Review personal-data obligations before distribution.


The manual Verified registry-bearing release candidate workflow requires the owner's distribution review, production-api environment secrets, complete snapshot acceptance, quality/security, secure vault and both native builds. The verified data artifact is downloaded by both platform jobs and embedded in their PyInstaller workers. Fresh primary workspaces initialize from the same checksum-verified database via exclusive atomic publication; an existing database is never overwritten and still uses its normal synchronization/import flow. Native smoke and local private-build acceptance must be rerun with real full data; large snapshots can exceed runner time, package size, memory, disk or startup budgets. ## Private owner enrollment (Windows and Linux)

Set the repository visibility to Private first. In an interactive terminal, authenticate GitHub CLI using its official `gh auth login` flow. Create the GitHub environment named `production-api` if needed. Then run `python tools/configure_registry_owner.py <actual-primary-workspace> --github`. The command verifies private visibility, accepts the OAuth pair via hidden input, tests the official API, writes the pair to the operating-system vault and sends both values to GitHub CLI over stdin as environment secrets. No plaintext key is written to Git or artifacts. The environment secrets are for collection at build time, not runtime credentials. On another Linux or Windows user profile, run local-only enrollment once (omit --github). Subsequent launches on that profile read the protected vault automatically. On Windows a private portable/installer build can use the existing vault via CRAWLVORA_PRIVATE_VAULT_DIR=<actual-primary-workspace>; the sealed DPAPI capsule is bound to that Windows account. The full mirror can use the same enrolled vault with `python tools/build_registry_bundle.py registry-bundle --authorized-workspace <actual-primary-workspace>`. The registry-bearing release workflow now refuses a public repository, including a second visibility check before publishing. Changing an existing private repository to public later exposes its release assets; never publish secret-containing artifacts. No automatic transfer of Windows DPAPI credentials to a Linux machine is attempted.


Local enrollment is independent of GitHub CLI authorization: run `python tools/configure_registry_owner.py <actual-primary-workspace>` first, then start the full isolated collection with `--authorized-workspace`. When GitHub CLI is authenticated and the existing production-api environment is available, run `python tools/configure_registry_owner.py <actual-primary-workspace> --github --reuse-vault`. The latter revalidates the live pair and verifies both environment secret names, without prompting again or overwriting the protected local record. Neither stage writes a plaintext credential file or changes environment protection rules.
