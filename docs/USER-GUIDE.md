# Crawlvora — Court Registry workspace

The sole online collection source is the Croatian Court Registry public v3 API. Existing local company records, source provenance and job history are retained. Web scraper jobs from old versions are cancelled rather than executed. CSV/JSON import and directory/registry exports remain available.

## Connection

In Settings, enter Client ID and Client Secret and apply them for the running session. Use Court Registry → Test connection, then authorize synchronization. For persistence across restarts, use the existing private `sudreg.private.json` in the user's application data directory (or set both `SUDREG_CLIENT_ID` and `SUDREG_CLIENT_SECRET` environment variables together). If either environment variable is explicitly set, the application uses the environment pair only; missing or empty values are not filled from a configuration file. The arbitrary working directory is no longer searched for credentials. Move any existing working-directory-only configuration to the private application data directory. Never commit credentials to GitHub. The desktop packages integrate the API client, not a shared secret. The scheduled refresh requires valid credentials and a running app.

## Existing data

The bundled original CSV contains 26,261 records and is seeded only once. Existing databases are not replaced. Reimport merges compatible OIB/MBS identifiers and conservative name/city/address matches; conflicting identifiers are not silently merged. Old sources remain visible solely as provenance, not as selectable online collection services. Import additional CSV/JSON through Import & Export.

## Synchronization

Use Court Registry to synchronize public bulk categories with the same snapshot ID, resume interrupted pages, browse records, compare completed snapshots and export. Official data updates compatible identity fields while retaining existing contacts. Tasks & Schedule provides the registry-only queue and weekday refresh.

Live credentials, complete synchronization, platform packaging and exact design parity must be verified before a production release.

## Data protection

Every normal launch acquires an OS workspace lock and creates a verified SQLite online backup before modifying an existing database. Backups are stored in the workspace's `backups` directory and are never automatically deleted. A failed backup prevents opening the workspace for changes. First-time seed import and its completion marker commit atomically. Differing incoming nonempty field values are retained in the local alternate_values table. These safeguards do not guarantee survival of disk failure: keep independent encrypted backups. For recovery, close all instances, copy the entire current workspace to a separate location, then restore a verified backup into a new workspace; never overwrite the only original. Backups contain business/contact data and must remain private.

Manual CSV/JSON imports also create a verified backup before writing. Company Profile → Source Links displays preserved alternative values and their source; directory JSON export includes these values as well. Directory exports are not complete workspace backups (they do not restore registry snapshots, all provenance or application state). Use the verified SQLite backup for complete workspace recovery. JSON import remains a directory import, not a database restore.

The utility checks full SQLite integrity, foreign keys and required tables, then creates and verifies a separate database. It never replaces the original database or backup. To inspect the recovered workspace using the source application, run `python tvrtk_scraper.py --data-dir /path/to/new-workspace`. Private credentials are not restored. The packaged desktop recovery UI and workspace selector are not implemented yet. Process-exit testing is not physical power-loss testing. Keep independent backups.

## Protected automatic backups

Open Settings → Backup & Recovery → Protected automatic backups. Initialize the catalog using a unique passphrase of at least 16 characters, or unlock the existing catalog. The passphrase and derived catalog authentication key are held only for the unlocked application session; no plaintext key file or hardcoded key is used. Automatic encrypted copies are scheduled every six hours and a catalog verification every 24 hours while unlocked. A verified encrypted copy is created before manual imports while unlocked; when locked, the existing unencrypted safety backup remains in use. The original startup backup remains unencrypted. No legacy copies are removed. The per-workspace catalog uses a passphrase-derived HMAC-SHA256 chain, authenticated head, SHA-256 ciphertext digests and SQLite FULL synchronous transactions. An archive committed before a crash but not registered in the catalog is reported as an orphan and retained; it can be recovered by the existing encrypted-file restore with the original passphrase. Catalog-authenticated restore creates a separate workspace, never silently activates it. A complete rollback of the catalog and archive directory cannot be detected without an independent trusted anchor. Periodic checks verify ciphertext against authenticated digests, not a full decrypt/restore of every archive. Secure erasure of temporary plaintext, unattended restart unlocking, OS-backed key storage and independent off-device replication are not implemented. Keep the passphrase and independently downloaded encrypted archive on separate storage. If the application cannot start, use the offline encrypted recovery utility from the source distribution.

The protected backup test suite now covers scheduled creation while unlocked, no repeated creation before the interval, locked-session behavior and forced child-process exit after encrypted archive publication but before catalog registration. The orphan remains recoverable using the existing encrypted-file recovery flow. The application never automatically switches to a stale backup.

## Native vault and independent replication

Opt in to secure key storage after unlocking an existing protected catalog. Windows uses user-scoped DPAPI with workspace-specific entropy and a separate profile directory; Linux uses `secret-tool` with the desktop Secret Service. No plaintext credential file is written. The Linux session must have an available, unlocked Secret Service. The vault holds the passphrase and an external catalog checkpoint, not a hardware monotonic counter. A prepared checkpoint is written before the catalog transaction and advanced after the exact new head is observed. An ambiguous old head after preparation fails closed and retains the archive for manual recovery. A missing enrolled vault is not silently replaced. This detects rollback of the workspace catalog against an intact vault; simultaneous rollback/deletion of both trust stores is not guaranteed detectable. Keep an independent passphrase and archive. Native vault loss does not delete existing data or prevent independent encrypted-file recovery. The existing unencrypted startup/locked-session safety copies remain.

Choose an existing directory on a separately mounted physical disk, then save the replica destination. The app rejects the source filesystem, copies authenticated archives without overwrite, checks SHA-256 and writes unique catalog snapshots. A different filesystem does not prove separate physical hardware. The target must support hard links (e.g. NTFS/ext4); external FAT/exFAT is not supported by the atomic publication path. Replica creation runs after new protected backups; errors retain the local copy. A restore test authenticates, decrypts and restores the selected archive into a temporary separate database, runs full integrity checks, and reports the company count. No automatic activation occurs. The vault, actual independent disk, native recovery downloads and power-loss behavior require final platform verification.

## Replacement-computer recovery

Export the authenticated recovery manifest alongside the selected protected archive and retain your original passphrase independently. The source utility `python tools/portable_recovery.py manifest.json protected-<id>.cvbackup new-workspace --expected-head <trusted-head>` verifies HMAC, archive digest, AES-GCM authentication and SQLite integrity before creating a separate workspace. The optional expected head must come from an independent trusted checkpoint, not the same potentially rolled-back disk. This is passphrase-based recovery, not an export of the machine-specific DPAPI/Secret Service secret. Replication writes per-archive manifests named with their catalog head. A new prepared vault checkpoint includes the signed entry so a verified interrupted append can roll forward exactly; older incomplete checkpoints lacking the entry remain blocked. No old catalog or archive is silently discarded.

The Recovery Center provides Download recovery manifest for the selected verified protected archive. Replication reuses a single authenticated catalog read instead of repeatedly reading the full catalog for each archive. Direct Linux block devices on the same physical disk are rejected even if partition filesystems differ. Virtual, network, RAID/LVM and Windows physical storage topology remain unverified; a separate filesystem is still not a universal physical-separation guarantee. A dedicated native vault acceptance workflow exercises real Windows DPAPI and an isolated Linux Secret Service session. Results must be checked before release.
